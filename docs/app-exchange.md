# События и вызовы между APP

У издателя объявите запись `type:"event"` в `run.settings.features`. Например, `mail.received` принимает объект с обязательным строковым полем `text`:

```json
{
  "mail.received": {
    "type":"event","description":"Получено письмо","version":"1",
    "schema":{"data":{"type":"object","required":["text"],"properties":{"text":{"type":"string"}}}}
  }
}
```

У получателя задайте разрешение на события источника и подписку в манифесте. Здесь `mailbox-id` — ID APP из `dir`. Для вызова метода издателя получателю дополнительно нужно разрешение `methods`.

```json
{
  "permissions":[{"node":"mailbox-id","events":"mail.received","methods":"message.extractText"}]
}
```

```json
{
  "executors":{"mode":"oneShot","poolSize":3},
  "subscriptions":[{"node":"mailbox-id","events":"mail.received","priority":10}]
}
```

После запуска обеих APP процесс издателя отправляет в stdout запрос `publish`. Для адресной отправки укажите `params.to` с ID получателя. Контроллер проверяет данные, пермиты получателя и его подписки. Получив событие в stdin, обработчик может послать запрос `call` в stdout и дождаться ответа в stdin. Полные сообщения приведены в [контракте JSONL](dev/runners/process.md).

В режиме `oneShot` общий пул APP допускает от 1 до 20 одновременных процессов. В режиме `persistent` работает один процесс. Укажите `idleTimeoutMs` для завершения простаивающего процесса, `null` отключает таймер. Для автоматических попыток восстановления задайте `maxRestarts` и подпишитесь на собственное событие `$.app.executor.failed`. Статус `working` позволяет принимать работу и при отсутствии процессов.

События и вызовы используют общую очередь на 100 ожидающих записей. Чем больше `priority`, тем раньше запись получит слот. При равных значениях сохраняется порядок поступления. При переполнении `canEvict:true` позволяет удалить старейшую запись минимального приоритета, если он не превышает приоритет новой. Для вызова эти поля задаются в описании метода. Вытесненный вызов получает ошибку.

## Личные подписки

Методы `$.node.subscriptions.get/set/add/delete/enable/disable` управляют личным списком APP. Эти операции требуют разрешения на соответствующий метод. Сначала проверяются правила манифеста, затем личные. Выключенное правило пропускается. Совпавший `deny:true` прекращает доставку. Первое разрешающее правило, для которого есть место, определяет приоритет события. Необязательное условие `caughtBy` проверяет, принял ли событие другой выбранный APP, доставку которому получателю разрешено наблюдать.

Для добавления передайте `{"subscriptions":[{"id":"inbox","node":"mailbox-id","events":"mail.received"}]}`. Личный ID уникален в пределах APP. Положение задают `before` или `after` со значением ID опорного правила. Значение `true` помещает правило в начало или конец. Для отключения передайте `{"ids":["inbox"]}` в `$.node.subscriptions.disable`. Замена, вставка и удаление проверяются целиком до сохранения. Уже принятые события сохраняют прежние приоритет и ID подписки.

## USER и подписки вкладки

Сессия USER может открыть `/ws/events` на хосте панели. WebSocket проверяет origin и действующую сессионную cookie. Каждое соединение начинает с пустым списком подписок. После переподключения вкладка устанавливает подписки заново. Команды передаются JSON-RPC 2.0:

```jsonl
{"jsonrpc":"2.0","id":1,"method":"subscriptions.add","params":{"subscriptions":[{"id":"mail","node":"mailbox-id","events":"mail.received"}]}}
{"jsonrpc":"2.0","id":1,"result":{}}
{"jsonrpc":"2.0","method":"event","params":{"from":"mailbox-id","event":"mail.received","subscription":"mail","data":{"text":"Привет"}}}
```

Подписка соединения содержит ID, селектор источника и имена событий. Команды `subscriptions.get/set/add/delete/enable/disable` управляют списком этой вкладки. Пермиты USER по-прежнему определяют доступные источники и события. Доставка USER подтверждается передачей хотя бы одному подходящему соединению. Контроллер не сохраняет пропущенные события для следующего входа.

Соединение поддерживает `dir`, `help`, `call`, `publish` и `cancel`. Для отмены передайте `{"id":42}` в параметрах `cancel`, где 42 — ID открытого запроса `call` на этом соединении. Завершение соединения снимает ожидание его исходящих вызовов.

## Сведения о доставке

В `publish` можно указать `delivery:"status"`, чтобы получить состояние доставки на момент публикации, или `delivery:"track"`, чтобы узнать итог передачи исполнителям. По умолчанию действует `"none"`. Для получателей требуется разрешение издателя `delivery:true`; собственную доставку издатель видит всегда. Пример ответа:

```json
{"publication":"publication-id","deliveries":[{"node":"receiver-id","status":"queued"}]}
```

`queued` означает, что событие принято, а запись в stdin ещё не подтверждена. `delivered` означает завершение записи в stdin или передачу в WebSocket. `rejected` означает отказ или очистку очереди. `unknown` означает, что результат передачи установить не удалось. `timeout` завершает отслеживание и оставляет событие в очереди.

В режиме `track` JSONL получает по одной строке `{"delivery":{"publication":"…","node":"…","status":"delivered"}}` для каждого видимого получателя, чей статус при публикации был `queued`. На WebSocket эти сведения передаются уведомлением `method:"delivery"`. Обычный HTTP RPC возвращает собранные итоговые состояния в ответе. Задайте `timeoutMs` от 1 до 86 400 000 мс. При отсутствии значения отслеживание ограничено сутками. Последующие уведомления привязаны к соединению издателя.
