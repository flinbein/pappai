# File-based manifests and the APP HTTP socket

The controller stores both the source and the applied JSON in SQLite. When creating an APP it obtains the stopped APP's ID within a savepoint, reads the file using the APP's effective permissions, validates the schema and publishes the configuration. An error rolls the database back to its pre-call state. The controller treats older records containing only a manifest as inline sources. The private platform database and its backups contain secrets.

One watcher per path serves all APPs that use it. Every 250 ms the watcher checks the name, file and link identifiers, size and timestamps. Its first pass also rereads the source to catch any replacement between the initial read and watcher setup. After a change, the next pass validates the data and permissions separately for each APP. On recovery the controller reconnects the watchers and rereads the files. The applied configuration determines `help`, subscriptions and assignments. While a persistent worker is running, the controller holds the most recently validated candidate until the worker exits.

The proxy looks up the APP by its public name. The controller checks its status, the permit and the current worker instance. Each process has a separately mounted private directory. The socket path inside the sandbox is `/run/pappai/http/app.sock`. On Linux the proxy opens the socket inode with `O_PATH | O_NOFOLLOW`, checks its type and connects through `/proc/self/fd`. This binds the connection to the verified inode even if the socket name is replaced. After route revocation, a stream already open on the previous process can finish. For HTTP the proxy strips the panel cookie from requests and strips domain cookies and cookies with panel cookie names from responses.
