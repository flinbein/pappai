# MCP для раннера Codex

Согласованная модель для внешнего раннера. Контроллеру ещё предстоит передавать политику исполнителя и отзывать назначения. Способ хранения OAuth и ограничения конфигурации проверены на настоящем Codex CLI 0.170.0 с локальными тестовыми серверами.

## Два источника подключений

PROFILE хранит общие определения MCP и авторизацию каждого сервера. APP выбирает нужные профильные подключения и может добавить свои серверы со своей авторизацией. Например, две APP работают с общей учётной записью сервера задач и каждая подключает личный календарь. При запуске раннер собирает для конкретного исполнителя список разрешённых серверов. Пустой список допустим.

Имя, адрес или команда запуска и источник учётных данных образуют одно подключение. При конфликте имён в выбранном наборе конфигурация требует исправления или отдельного имени. Замена адреса не переносит секрет на новый сервер. Локальная авторизация принадлежит ID APP и переживает перезапуск. Копия манифеста её не получает.

Предлагаемые методы раннера доступны на целевой ноде PROFILE или APP. Вызов сначала проходит стандартную проверку права на метод.

| Метод | Эффект |
|---|---|
| `codex.mcp.get` | Перечисляет настройки и состояние подключения, скрывая секреты. Чтение не запускает MCP. |
| `codex.mcp.set`, `codex.mcp.delete` | Меняют запись у соответствующего владельца. Удаление также очищает локальные секреты и незавершённую авторизацию записи. |
| `codex.mcp.auth`, `codex.mcp.logout` | Авторизуют подключение или удаляют сохранённый локальный доступ. Отзыв разрешения у провайдера зависит от его API. |
| `codex.mcp.test` | Проверяет соединение, MCP initialization и обнаружение инструментов. Проверка не выполняет произвольный инструмент. |

Для настройки, требующей запуска программы или обращения в сеть, предел на PROFILE — пересечение эффективных прав вызывающего и PROFILE. На APP дополнительно учитываются права целевой APP и её выбранного профиля. Контекст определяется адресатом метода и действующим вызовом. Параметр выбора другой APP для заимствования её прав не предусмотрен. Рабочий исполнитель ограничен [пересечением прав APP и PROFILE](profiles.md).

У нативного `codex mcp login` есть ограничение по транспорту. На 0.170.0 вызов для stdio вернул ошибку «OAuth login is only supported for streamable HTTP servers», сама команда MCP не запустилась. Поэтому для такого stdio метод `auth` может сразу вернуть ошибку неподдерживаемого способа входа. Если раннер впоследствии предоставит собственную процедуру настройки stdio, для её запуска действуют те же пермиты и песочница.

## Граница доверия

- **HTTP MCP.** Если эффективный `network:false`, раннер исключает HTTP-сервер ещё до инициализации, включая локальный шлюз к профильной авторизации. Это правило относится и к тесту и авторизации MCP. Соединение самого Codex с моделью является отдельным служебным каналом.
- **stdio MCP.** Любую пользовательскую команду, включая запуск для `auth` или `test`, выполняет доверенная обёртка внутри bubblewrap. Она строит монтирования, сеть и окружение из фактического назначения. Если изоляцию создать не удалось, запуск завершается ошибкой. Служебные каталоги профилей, конфигурации, программы запуска и ключи шлюза должны оставаться вне доступа команды, в том числе при широком разрешении на родительский каталог.
- **Настройки Codex.** Доверенный раннер формирует список серверов и защищённые ограничения для каждого исполнителя. Отдельного `CODEX_HOME` недостаточно. Codex также читает настройки доверенного проекта. В проверке сработал приватный для исполнителя `/etc/codex/requirements.toml` с разрешёнными именами и HTTP-адресами. Для stdio необходимо связать вызов обёртки с назначением контроллера. Совпадение имени команды само по себе не удостоверяет аргументы, окружение и рабочий каталог. Пользовательские исполняемые помощники конфигурации также требуют контролируемого запуска.
- **Завершение.** Раннер владеет песочницей stdio и закрывает её при отзыве доступа, остановке исполнителя или обрыве управляющего соединения. EOF может штатно остановить MCP. Принудительное завершение через владельца песочницы нужно и для сервера, который EOF не обрабатывает.

## Общий OAuth и ротация

Для каждого общего разрешения нужен один владелец обновляемого токена. В рабочем прототипе профильный app-server хранит нативную авторизацию в своём изолированном `CODEX_HOME`. Два отдельных app-server исполнителей обращаются к нему через аутентифицированный локальный шлюз. Каждый хранит собственную авторизацию локальных MCP в своём каталоге. У MCP OAuth с файловым хранилищем Codex отдельный файл `.credentials.json`. Импорт авторизации самого Codex через `auth.json` описан в [профилях](profiles.md).

При ротации общего refresh token старая копия перестаёт работать. Простое копирование профильного файла в каждый APP приводит к отказу при последующем обновлении. Общий владелец должен координировать refresh; шлюз обязан проверять назначение на каждом подключении и прекращать доступ при отзыве. Прототип проверяет один инструмент через шлюз. Полная поддержка MCP, защита ключа шлюза, восстановление владельца и проверка отзыва на действующем исполнителе входят в приёмку интеграции.
