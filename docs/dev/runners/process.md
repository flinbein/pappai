# Раннер process

В первой сборке раннер запускает одноразовый процесс на каждый вызов. Контроллер держит один слот на APP. В планах v1 также предусмотрены постоянные процессы для потока событий.

## Как передаётся вызов

Контроллер отправляет назначение хосту раннера через приватный IPC. Хост запускает процесс из подготовленного манифеста. В stdin исполнителя попадает одна строка JSONL:

```jsonl
{"from":"chat-agent","id":"call-7","method":"message.extractText","data":{"text":"  Привет  "}}
```

Ответ приходит в stdout отдельной строкой:

```jsonl
{"id":"call-7","result":"Привет"}
```

Строка задаёт границу сообщения. Одно чтение из pipe может вернуть половину строки или несколько строк. Обработчик читает до перевода строки и может ответить, пока stdin открыт. Если успешный ответ нарушает схему, контроллер возвращает ошибку в stdin. Исполнитель может исправить ответ с тем же ID. Завершение процесса освобождает слот. Потеря ответа после внешнего действия допускает уже совершённый эффект, поэтому ядро автоматически его не повторяет. [Пример скрипта](../../../examples/extract-text/extract.cjs) · [Манифест](../../../examples/extract-text/manifest.json)

IPC хоста отделён от JSONL скрипта. Хост сам проставляет APP и системный ID назначения и принимает ответы только на него. Сбой запуска возвращает контроллеру ошибку. Диагностика процесса идёт в stderr. Для аварийного выхода хост пишет в свой журнал последние 2 КиБ диагностики исполнителя.

## Как запускается песочница

Полная применимая цепочка `permissions:null` допускает доверенный запуск непосредственно в ОС. При наличии ограничений Linux-раннер использует bubblewrap и завершает запуск ошибкой, если изоляцию подготовить невозможно.

В первой сборке доступны положительные выдачи на существующие абсолютные пути обычных файлов и каталогов без символических ссылок. Корректные гранты подключаются по тем же путям. Явная выдача корня и служебных путей `/proc`, `/dev`, `/sys`, `/run`, `/tmp` и их потомков пока отклоняется. Песочница получает новые `/proc` и `/dev`, личный каталог APP как `/tmp` и системные `/bin`, `/sbin`, `/lib`, `/usr`, `/etc` на чтение. Рабочий каталог сам по себе не выдаёт его содержимое. При запрете сети процесс получает отдельное сетевое пространство имён.

Хост ограничивает время жизни процесса, если задано `maxLifetimeMs`. При остановке он отправляет SIGINT, через 10 секунд — SIGKILL. При аварии самого хоста процессы песочницы завершаются средствами bubblewrap и PID namespace. Фоновые потомки доверенных процессов вне песочницы могут пережить хост. Хост каждого раннера принадлежит одному контроллеру.

## Проверки Linux

Для запуска в Alpine нужны Node.js 24 или новее, зависимости проекта и bubblewrap. В конфигурации Docker Desktop с Linux-контейнерами подтверждены следующие проверки:

- С `--cap-add SYS_ADMIN --security-opt seccomp=unconfined` задать `PAPPAI_TEST_BWRAP=1` и выполнить `node --test tests/runner.test.ts tests/runner-loss.test.ts` из каталога проекта. Тесты проверяют монтирование отдельного файла, скрытый соседний файл, отдельную сеть, отказ в доступе к содержимому рабочего каталога и последствия аварии общего раннера.
- С обычными ограничениями Docker, при которых запрещено создание namespace, задать `PAPPAI_TEST_BWRAP_DENIED=1` и выполнить `node --test --test-name-pattern "failed OS" tests/runner.test.ts`. Проверка ожидает ошибку изоляции и отсутствие ответа исполнителя.

Эти параметры Docker зависят от политики хоста. Контейнер для проверок содержит также каталог `tests/`; в поставляемый образ приложения он не входит.
