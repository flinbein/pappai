# Раннер process

Раннер `process` исполняет методы и получает события по подписке. Контроллер хранит очередь, проверяет контракт и резервирует слот до запуска процесса. [Настройка пула и подписок](../../app-exchange.md)

## Обмен через stdin и stdout

Каждая запись заканчивается переводом строки. События, входящие вызовы и ответы на собственные запросы процесса поступают в один stdin. Одно чтение из pipe может вернуть несколько строк или часть строки. Для Node.js подходит `readline.createInterface({input:process.stdin})`.

Входящий вызов и его ответ в stdout:

```jsonl
{"from":"chat-agent","id":"call-7","method":"message.extractText","data":{"text":"  Привет  "}}
{"id":"call-7","result":"Привет"}
```

Событие занимает одну строку stdin. При доставке по личному правилу оно содержит ID этого правила:

```jsonl
{"from":"mailbox","event":"mail.received","subscription":"inbox","data":{"text":"Привет"}}
```

Процесс отправляет собственный запрос в stdout. Ответ с таким же локальным ID возвращается в stdin того же экземпляра:

```jsonl
{"id":"request-1","method":"call","params":{"node":"extract","method":"message.extractText","data":{"text":"  Привет  "},"timeoutMs":5000}}
{"id":"request-1","result":"Привет"}
```

`dir` и `help` используют те же пермиты APP, что и её вызовы. Для публикации процесс указывает событие из своего действующего контракта:

```jsonl
{"id":"request-2","method":"publish","params":{"event":"mail.received","data":{"text":"Привет"}}}
{"id":"request-2","result":{}}
```

Контроллер определяет источник по приватному IPC хоста. Он связывает каждый ответ с APP, экземпляром и открытым вызовом. Неверный результат по выходной схеме возвращает ошибку в stdin. Исполнитель может исправить результат с тем же системным ID. Завершившийся, отменённый или просроченный вызов закрывает полномочия обработчика на ответ. Побочные эффекты не воспроизводятся автоматически. Диагностика процесса идёт в stderr. При аварийном выходе хост пишет в журнал последние 2 КиБ этой диагностики. [Пример обработчика](../../../examples/extract-text/extract.cjs)

## Выдача работы

В режиме `oneShot` процесс получает одну запись. Канал stdin остаётся открытым для ответов на его запросы, слот занят до выхода процесса. В `persistent` один процесс получает каждую следующую запись сразу после того, как запись предыдущей строки в stdin завершилась. Когда pipe заполнен, остальная работа ждёт в ограниченной очереди контроллера. Хост принимает до 32 одновременно открытых запросов от одного процесса. Локальные ID запросов — уникальные среди открытых непустые строки до 255 символов.

Старт APP включает приём работы. Первая подходящая запись запускает процесс. Для фонового сервиса можно подписаться на `$.app.statusChanged`, `$.workspace.init` и `$.app.restarted`. При разрешённой повторной попытке после сбоя постоянного процесса публикуется локальное `$.app.executor.failed`. Если попытки исчерпаны, APP переходит в `error` и освобождает очередь. Ручной рестарт сохраняет очередность, дедлайны и принятые события. Уже переданные вызовы при выходе процесса без ответа получают ошибку. Исполнители `oneShot` завершают принятую работу. При изменении контракта ожидающие вызовы проверяются по новому входу и версии, результат проверяется по действующему выходу.

## Как запускается песочница

Полная применимая цепочка `permissions:null` допускает доверенный запуск непосредственно в ОС. При наличии ограничений Linux-раннер использует bubblewrap и завершает запуск ошибкой, если изоляцию подготовить невозможно.

Linux-раннер строит монтирования по разрешённым путям и исключениям APP. Для явных файловых грантов нужны существующие абсолютные пути без символических ссылок. Песочница получает новые `/proc` и `/dev`, личный каталог APP как `/tmp` и системные `/bin`, `/sbin`, `/lib`, `/usr`, `/etc` на чтение с учётом масок. Рабочий каталог сам по себе не выдаёт его содержимое. При запрете сети процесс получает отдельное сетевое пространство имён.

Хост ограничивает время жизни процесса, если задано `maxLifetimeMs`. При остановке он отправляет SIGINT, через 10 секунд — SIGKILL. При аварии самого хоста процессы песочницы завершаются средствами bubblewrap и PID namespace. Фоновые потомки доверенных процессов вне песочницы могут пережить хост. Хост каждого раннера принадлежит одному контроллеру.

## Проверки Linux

Для запуска в Alpine нужны Node.js 24 или новее, зависимости проекта и bubblewrap. В конфигурации Docker Desktop с Linux-контейнерами подтверждены следующие проверки:

- С `--cap-add SYS_ADMIN --security-opt seccomp=unconfined` задать `PAPPAI_TEST_BWRAP=1` и выполнить `node --test tests/runner.test.ts tests/runner-loss.test.ts` из каталога проекта. Тесты проверяют монтирование отдельного файла, скрытый соседний файл, отдельную сеть, отказ в доступе к содержимому рабочего каталога и последствия аварии общего раннера.
- С обычными ограничениями Docker, при которых запрещено создание namespace, задать `PAPPAI_TEST_BWRAP_DENIED=1` и выполнить `node --test --test-name-pattern "failed OS" tests/runner.test.ts`. Проверка ожидает ошибку изоляции и отсутствие ответа исполнителя.

Эти параметры Docker зависят от политики хоста. Контейнер для проверок содержит также каталог `tests/`; в поставляемый образ приложения он не входит.
