# Профили раннеров

Контроллер хранит ноды PROFILE, проверяет область действия и пермиты исполнителей. Профиль создаётся выключенным. Для привязки используйте `profile` в `$.app.create` или `$.app.profile.set({profile})`. Для проверки состояния доступны `$.profile.get` и `$.app.get`. [Пример настройки Codex](../../codex.md)

## Что хранит профиль

PROFILE — лист дерева workspace/TEAM со своим ID, именем и состоянием. В одном профиле могут быть независимые подключения нескольких установленных раннеров. У профиля нет очереди и исполнителей. Служебные методы ноды управляют её жизненным циклом и областью действия (`scope`). Возможность создать профиль в TEAM или настроить конкретное подключение выдаётся обычными пермитами на методы. Те же методы доступны USER из панели и агенту, действующему от имени своей APP.

APP хранит необязательный ID профиля в собственных настройках. Манифест выбирает раннер через `run.type`. Копирование или обновление манифеста само по себе не меняет привязку к профилю. При запуске раннер получает доступ к своему подключению. История сессии и рабочее состояние каждого исполнителя хранятся отдельно от общего подключения.

## Кому доступно подключение

Поле `scope` профиля по умолчанию равно `[]`. Оно выбирает APP по общим [правилам селекторов](../../permissions.md). Право распространяется на все подключения этого профиля, включая добавленные позднее. Для подключения с другим кругом пользователей создают отдельный PROFILE.

Например, `["!support-agents/**", "support/**"]` разрешает профиль потомкам TEAM с ID `support` за исключением потомков `support-agents`. Список из двух точных ID разрешает двум APP из разных TEAM пользоваться одним личным профилем. Проверяется ID самой APP. Членство пользователя, который создал APP или вызвал её метод, не переносится на APP.

Сохранить `APP.profile` можно до включения APP в `scope`. Перед каждым запуском контроллер проверяет, что выбранный профиль существует, включён и допускает эту APP. Раннер, которому нужна авторизация, дополнительно проверяет своё подключение. Ошибка переводит APP в `error` без автоматических повторных запусков и без подстановки учётной записи хоста.

Встроенный `process` можно запускать с пустым или отсутствующим `profile`. Тогда действуют собственные права APP. При явно указанном PROFILE даже этот раннер проверяет профиль и ограничивает исполнителя пересечением прав, хотя отдельная учётная запись для запуска процесса ему не нужна.

## Права исполнителя

Для каждого действия с выбранным профилем контроллер отдельно вычисляет обычный результат для APP и для PROFILE. Оба должны разрешить действие. Это касается файлов, сети, вызовов методов и прочих операций контроллера. Результат проверки `scope` сам по себе никаких дополнительных прав не выдаёт. Источником вызова или события остаётся APP. Относительный селектор в правиле вычисляется от владельца правила.

Например, если APP разрешена запись во весь `/projects`, а PROFILE разрешено только читать `/projects/team`, исполнитель сможет читать внутри `/projects/team`. Если APP разрешена сеть, а PROFILE запрещена, сетевые инструменты исполнителя остаются без сети. Вычисление пересечения должно сохранять порядок правил и разрешения по членству внутри каждого субъекта. Пустое значение у APP, снимающее привязку к ограничивающему профилю, может расширить доступ. Разрешения на создание и редактирование APP должны учитывать право изменить эту привязку.

## Изменение доступа

При резервировании запуска контроллер запоминает фактические ID профиля, APP и исполнителя. При изменении `scope`, членства или положения ноды в дереве он заново проверяет затронутых исполнителей по новому состоянию дерева. Исполнитель, потерявший доступ, сразу прекращает получать новые задания и проходит штатное завершение. Если запуск ещё можно отменить, его отменяют. Уже стартовавшему процессу с отозванным доступом первое задание не передают.

| Ситуация | Результат |
|---|---|
| Доступ потерял текущий постоянный исполнитель | APP сразу переходит в `error`. Очередь очищается по обычным правилам ошибки. |
| Доступ потерял одноразовый исполнитель | Он штатно завершается. Для одноразовой или спящей APP ошибка возникает при первой неудачной попытке запуска. Уже ожидающий в очереди вызов может вызвать её сразу после освобождения слота. |
| Старый исполнитель заканчивает работу после смены профиля APP | Отзыв затрагивает только исполнителей, действительно использующих отозванный профиль. Новый исполнитель и статус APP сохраняются. |

Уже принятое задание может завершиться за время штатной остановки. При выходе без ответа вызов завершается ошибкой. Контроллер не возвращает такое задание в очередь для повторной доставки: внешнее действие могло уже состояться.

Отключение PROFILE отзывает доступ ко всем его подключениям по этим же правилам. Включение снова открывает доступ по действующему `scope`. APP в состоянии ошибки запускают обычной командой `start`. Для вывода профиля из эксплуатации доступны отключение, удаление авторизации конкретного раннера и отвязка APP. Полное удаление ноды с очисткой у всех установленных раннеров отложено.

## Настройка через установленный раннер

Раннер объявляет методы в пространстве своего зарегистрированного имени, например `codex.setup`, `codex.status`, `codex.remove`. Контроллер публикует их описания и схемы в `help` ноды PROFILE. Вызов направляется доверенному хосту раннера напрямую. Для настройки достаточно пермита на метод; выключенный профиль и пустой `scope` допускают настройку до запуска APP. `codex.remove` удаляет только подключение Codex.

Каждому подключению выделяется служебный каталог, например `$PAPPAI_PROFILES_DIR/{profileId}/{runnerName}/`. Раннер определяет допустимые способы настройки, проверяет входные данные и хранит файлы своего подключения. Неудачный импорт сохраняет ранее рабочее подключение. Статус может сообщать об импорте и отдельно об успешной проверке доступа; секреты не входят в ответы и справку.

Пример запроса USER или агента с заранее подготовленным файлом:

```json
{
  "node": "support-profile",
  "method": "codex.setup",
  "data": { "authFile": "/tmp/codex-auth.json" }
}
```

1. Ядро проверяет пермит вызывающего на метод и аргументы. Раннер получает `caller`, `callId` и исходные данные. Сам раннер знает, что означает `authFile`.
2. Раннер отправляет `profileRead` с ID вызова, ID запроса чтения и путём. Контроллер проверяет, что вызов открыт и назначен именно этому хосту. Он определяет фактического инициатора и, для APP, экземпляр исполнителя.
3. Контроллер открывает обычный файл в представлении инициатора с проверкой текущих прав. При успехе `profileFile` передаёт до 1 МиБ содержимого доверенному хосту. У песочного process путь `/tmp` разрешается в его приватном каталоге. Изолированный Codex имеет собственный tmpfs, для которого чтение через контроллер недоступно.
4. Раннер проверяет и атомарно сохраняет авторизацию. Закрытие вызова прекращает новые запросы чтения.

В этом интерфейсе не требуются объявление `fileInputs` и дублирование пути в `call.read`. Ядро проверяет запрошенный доступ и не интерпретирует произвольные строки внутри `data`. Доверенный раннер технически может запросить другой путь в пределах прав инициатора; контракт метода определяет, какие файлы ему нужны. Для передачи файлов между обычными APP действует [делегирование в рамках вызова](../../delegated-files.md).

Порядок [установки Codex CLI](codex.md) и [права MCP](mcp.md) входят в проект внешнего раннера.
