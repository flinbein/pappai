# План разработки

В первой сборке работают вход по passkey, дерево нод, вызов одноразовой APP с одним слотом и веб-терминал USER. [Проверки первой сборки](first-milestone.md)

| Этап | Критерий готовности |
|---|---|
| Воспроизводимый выпуск | Образ собирается из отмеченной версии исходников. На отдельной установке проверено восстановление нод, настроек и пользовательских файлов из копий двух томов. |
| Управление APP | В панели видны статус, последняя ошибка, исполнитель и очередь. Администратор останавливает APP с активным и ожидающим вызовами, меняет встроенный манифест и вызывает обновлённый метод после запуска. |
| Обмен между APP | Процесс получает событие по подписке, вызывает метод другой APP и читает ответ из stdin. Контроллер применяет пермиты и соотносит ответы с вызывающими при нескольких занятых слотах. |
| Постоянный сервис | APP с файловым манифестом, override и секретным токеном принимает webhook. После рестарта HTTP поступает новому исполнителю. |
| Передача файлов | Две изолированные APP передают файл в рамках открытого вызова. Завершение, отмена и таймаут вызывают отзыв делегированного доступа. |
| Codex и веб-чат | Одноразовое поручение возвращает результат по схеме. Постоянная сессия сохраняет историю чата после переподключения. |

Перед подключением MCP к раннеру Codex нужно определить, от чьего имени выполняется запрос, какие права получает сервер и как отзывается доступ. Проверка должна охватывать и серверы из пользовательской конфигурации Codex. Среди дальнейших задач v1 также членство TEAM, расширение пермитов, SMTP-восстановление и управление реестром раннеров.
